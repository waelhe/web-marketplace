# مواصفة تصميم: لوحة الإدارة (الدفعة ٣ — إغلاق نطاق العقد الإداري)

> **الحالة:** الدفعة الثالثة من خطة رفع التغطية — كلمة المالك «نفّذ وتحقق» (2026-09-25) فتحت تنفيذها؛ كل قسم هنا قفه على قياس حي مؤرّخ (جلسة qa-tester منعشة، 2026-09-25 — إعادة قياس كاملة قبل الكتابة) أو `ملف:سطر` — لا اجتهاد.
> **المصدر الحاكم:** عقد OpenAPI الحي (staging `/v3/api-docs` — مقارنة sha256 مع نسخة المهمة 24: **مطابق بالبايت**) + كود مستودع الباك اند (البوابات من المصدر) + الوثائق المحزومة (Next 16.3.5).
> **نقطة الانطلاق المقيسة:** 80/97 = 82.5% من نطاق المستخدم (المهام 23–25، في الإنتاج). هذه الدفعة تفتح **نطاق الإدارة** المقيس: 9 عمليات (الإشراف ×2 + قواعد التسعير ×5 + تأكيد/استرداد الدفع ×2) على قناة موثوقة رسمية واحدة.

## القسم 1 — الطابور الإشرافي (عمليتان)

على المسار الجديد `/admin` (مصادق؛ مجهول → بوابة تسجيل الدخول + `noindex` — عقد الخصوصية نفسه لكل الأسطح الخاصة): قسم «بلاغات الإشراف» يقرأ `GET /api/v1/admin/reports?page=0&size=20` (الفاترة FIFO كاملة؛ `?status=` اختياري) ويعرض صفوف `ContentReportView` (النوع موجود أصلاً في community-contract.ts من الدفعة ٢). لكل بلاغ مفتوح نموذج تسوية: `action` (DISMISS | HIDE_CONTENT — select) + `note` اختياري ≤2000 → Server Action → `POST /api/v1/admin/reports/{reportId}/resolve` ثم `refresh()`. action غير صالح = 400 بيت الكلمات يسرد القاموس (parse قبل أي استدعاء — المصدر).

## القسم 2 — مدير قواعد التسعير (5 عمليات)

قسم «قواعد التسعير» على اللوحة نفسها: القائمة `GET /api/v1/pricing/rules` (مصفوفة كاملة — لا ترقيم) بنموذج إنشاء `POST` (201): `name` إلزامي ≤200، `category` اختياري ≤100، `taxRate` و`discountPct` اختياريات عشريتان 0..1 (Bean Validation من المصدر — كلمات الخلفي تُعرض حرفياً). لكل صف: «فعّل» `PUT …/{id}/activate` / «عطّل» `PUT …/{id}/deactivate` (الاستجابة = الصف المحدّث) و«احذف» `DELETE …/{id}` (204) — كلها Server Actions بفحص الجلسة + `backendSend` + `refresh()`.

## القسم 3 — إدارة المدفوعات (عمليتان + قراءة العرض)

قسم «المدفوعات»: القائمة `GET /api/v1/admin/payments?page=0&size=20` (ملخصات القصص: المعرّف/الحجز/المستهلك/المبلغ/العملة/الحالة/المسترد). نموذجان:
- **«أكّد القصد»**: معرّف قصد (يُنسخ من صف القائمة) + `externalId` إلزامي → `POST /api/v1/payments/intents/{id}/confirm {externalId}` → استجابة القصد الكاملة تُعرض.
- **«استرد دفعة»**: معرّف **دفعة** (ليس القصد!) بصراحة نصية كاملة: معرّفات الدفعات لا تظهر في أي قراءة عقدية — مصدرها استجابة refund نفسها وسجلات بوابة الدفع → `POST /api/v1/payments/{paymentId}/refund` → `PaymentResponse` (id/amountCents/status/التواريخ) تُعرض.

## حدّ الصدق المُلزم للوحة كلها (قياس #9)

الواجهة تعرض فوق الأقسام إقراراً ثابتاً: اللوحة للإدارة؛ حساب غير الأدمن يرى رفض الخلفي الحرفي (403 AUTHZ-001 المقيس) — والحقول السعيدة (صفوف الطابور، إنشاء القواعد، التأكيد/الاسترداد) **غير قابلة للتحقق بحساب الاختبار** لغياب اعتمادات أدمن عندنا؛ التصميم ضد العقد الرسمي والمصدر، والخلفي هو السلطة الوحيدة.

## بوابات ما قبل التنفيذ

- كل كتابة عبر Server Action: فحص جلسة + `backendSend` + كلمات problem+json حرفياً + `refresh()` (نمط المستودع ×10 + refresh.md المحزومة).
- **خطة التحقق الملزمة**: lint → `tsc` → `build` بالمثبتة `../.tools/node-v26.8.2` + حلقة next-dev-loop (MCP `get_compilation_issues` صفر + `get_errors` صفر + `agent-browser` سلوك مقيس) + **دمج محلي فقط — لا دفع إلا بكلمة المالك**.
- بطارية حية عبر BFF (القناة نفسها): مجهول → بوابة + noindex؛ مصادق (qa-tester) → الأقسام الثلاثة تقرأ و**رفض 403 الحرفي يُعرض** (كلمات القياس #8 حرفياً)؛ نموذج تسوية/إنشاء/تأكيد يُرسل → رفض 403 نفسه في حالة الإجراء (نمط الفشل الصادق)؛ البنية سليمة بعد reload بلا أخطاء hydration.
- تحديث قسم Routes في AGENTS.md للمسار الجديد الوحيد (`/admin`) ضمن نفس الدفعة (البلوك المُدار لا يُلمس).
